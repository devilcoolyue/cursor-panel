# v0.0.11 版本归档

v0.0.11 将添加和重新授权账号改为在浏览器中确认登录，修复 Cursor 新增网页风控后粘贴 Cookie 无法添加账号的问题，并改进被 GitHub 限流时的检查更新。Python、Web、桌面及随包后台统一为 `0.0.11`；API 主版本保持 `1`，数据库 schema 保持 `0004_retention`。

## 更新内容

- **在浏览器中授权账号**：Cursor 的网页登录回调先后加入 CSRF 校验和 Castle 风控，风控凭据只能由 Cursor 页面在浏览器中生成，面板在浏览器外提交 Cookie 会被拒绝（v0.0.9 / v0.0.10 显示“服务请求失败”）。现在「添加账号」和「重新授权」改为点击「在浏览器中授权」：面板打开 Cursor 登录确认页（与 Cursor 编辑器登录相同），用户在浏览器中用对应账号确认后，后台自动领取并验证桌面凭证、拉取额度后保存。无需再复制或粘贴 Cookie，新账号也不再保存 Cookie。
- **授权流程边界**：确认页 5 分钟内有效，仅发起人可查询或取消，关闭表单即取消。重新授权时若浏览器确认了其他 Cursor 账号会明确提示且不覆盖原账号；新增已存在的账号会提示改用重新授权。
- **已有账号不受影响**：已添加账号继续用刷新令牌自动续期，额度刷新和切换照常可用。没有刷新令牌的早期导入记录会标记为需要重新授权。
- **检查更新更稳定**：GitHub 匿名 API 按出口 IP 每小时限 60 次，共用网络时容易触发“发布服务暂不可用”。被限流或无法访问 API 时，客户端改读最新 Release 的签名更新清单获取版本；仍失败时提示需等待的分钟数。更新包继续由签名验证。
- **其他**：`cursor-quota -c` 改为逐个账号在浏览器中确认后查询；旧版 Cookie 授权接口返回 410 并说明原因；帮助与使用文档同步更新。

## 实际验证

使用真实账号逐步诊断确认：Cookie 方式在网页回调处被 Castle 风控以 403 拦截；浏览器确认方式经用户在本机浏览器确认后，领取桌面凭证、桌面身份校验及 6 个额度接口全部返回 200。诊断只输出状态码，未记录 Cookie、Token 或邮箱，未保存签发的会话。

本地 Python 完整回归 396 项中 386 项通过，10 项因缺少 PowerShell 跳过；随包后台 9 项、Rust 7 项通过。Web、桌面、远程连接、启动卡片与更新的真实浏览器流程通过（本机使用已安装的 Chromium 无头版本），覆盖新增、重新授权、账号不一致提示及删除。

## 安装与升级

[GitHub Release v0.0.11](https://github.com/devilcoolyue/cursor-panel/releases/tag/v0.0.11) 提供 macOS Apple Silicon / Intel、Windows x64、Linux amd64 服务端、Python wheel、源码、校验文件和签名更新产物。

- 已安装 `v0.0.10` 的客户端可在“关于与更新”检查并安装 `v0.0.11`，或完全退出后使用完整安装包覆盖升级。
- 连接远程实例时，需服务端也升级到 `v0.0.11` 才能使用浏览器授权；旧客户端连接新服务端时，Cookie 授权会被拒绝，请同时升级客户端。
- 本次不改变应用标识、数据目录、系统凭证库、更新签名密钥及数据库 schema，已有账号、凭证、连接和显示偏好保持不变。

## 发布验证

固定发布流程会在发布前执行完整后端回归、三种桌面架构的浏览器与系统验证、随包后台回归、安装后启动检查、Linux 镜像与 wheel 验证、更新签名及全部附件校验。只有全部成功后才创建并公开 `v0.0.11`。
